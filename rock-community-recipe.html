Guess Who? A Photo Name Game in Rock with Lava and HTMX

Teach your team names, one face at a time, with a Lava block that swaps in the next question through HTMX instead of a full page reload.

LevelIntermediate
RequiresRock RMS 18.0+
AuthorGerry Miller, Triumph Tech
Summary: A Lava block shows a random person's photo and asks the player to guess their name, then swaps in the result and the next question with HTMX, no full page reload and no JavaScript framework. The roster is not hardcoded anywhere. It is built live from Rock Tags, so any church can point this at its own people and its own database without touching a line of code.

Why this recipe

The Recipes library has plenty on communications, check-in, and giving, but not much showing HTMX driving interactivity inside Rock. HTMX is a small library that lets a page ask the server for a fragment of new HTML and swap it into place, no build step, no client-side framework, no page reload. This recipe uses a name-guessing game as an approachable, low-stakes vehicle for that pattern, because the technique underneath (partial swaps inside a Lava block, a server-side random pick, and game state carried through the request) generalizes far beyond a game.

Knowing people's names is foundational to belonging and pastoral care, and it is one of the hardest things for a growing church to keep up with. This turns name-learning into a fast, repeatable habit for greeters, small group leaders, new staff, and serving-team volunteers, without adding anything to anyone's plate.

Prerequisites

  • Rock RMS 18.0 or later, no exceptions. That version introduced both the Lava Applications feature and the built-in {[ dropdown ]} shortcode this build depends on. Check Admin Tools > CMS Configuration for a Lava Applications item; if it is not there, this recipe will not run yet.
  • HTMX loaded on the page or in the theme.
  • A pool of people to draw from, each with a profile photo on file.

How the roster is sourced

Most recipes like this ask you to configure a group, a campus, or a data view up front. This one does not. Who is in the game is driven entirely by Rock Tags: tag the people you want, one at a time from a Person profile or in bulk from a Grid, and any active, organization-wide, Person-scoped tag shows up automatically in the setup screen's dropdown. Adding a new list is a staff action in Rock, not a code change or a redeploy.

The setup endpoint builds that dropdown with a plain SQL query against Rock's own Tag and EntityType tables: 

SELECT t.Id, t.Name
FROM Tag t
JOIN EntityType et ON et.Id = t.EntityTypeId
WHERE et.Guid              = '72657ED8-D16E-492E-AC12-144C5E7567E7' -- Person
  AND t.OwnerPersonAliasId IS NULL   -- organization-wide, not a personal tag
  AND t.IsActive            = 1
ORDER BY t.[Order], t.Name

OwnerPersonAliasId IS NULL is the detail worth noticing: it excludes personal tags owned by a single staff login, so one person's private tags never clutter everyone else's dropdown. Only tags meant to be shared show up.

People without a profile photo are skipped automatically wherever the deck is built, so the game never shows a blank or placeholder image. If a tagged list looks smaller than expected, that is almost always why.

Building the deck

Once a tag is chosen, the game endpoint builds a shuffled deck from everyone carrying that tag who also has a photo on file and an active record status: 

SELECT Id
FROM (
  SELECT DISTINCT p.Id
  FROM TaggedItem ti
  JOIN Person p ON p.Guid = ti.EntityGuid
  WHERE ti.TagId             = @tagId
    AND p.PhotoId             IS NOT NULL
    AND p.RecordStatusValueId = 3
) AS TaggedPeople
ORDER BY NEWID()

The inner query deduplicates in case someone was tagged more than once with the same tag; SQL Server will not allow ORDER BY NEWID() directly against a SELECT DISTINCT, so the random shuffle happens in an outer query that wraps it instead. The resulting Id list becomes the deck, carried through the rest of the game entirely in the query string (deck order, current index, score), so a page reload never depends on server-side session state.

Wiring up HTMX

Every screen after the initial load is a normal link with href="#" and an hx-get attribute pointing at the next fragment, targeting the same container the whole game lives in: 

<a href="#" hx-get="{{ nextCardUrl }}" hx-target="#rolodex-app" class="btn btn-success btn-lg btn-block">
  Next <i class="fa fa-arrow-right"></i>
</a>

Rock's Lava Applications support a shorthand for calling one endpoint from another: ^/{applicationSlug}/{endpointSlug} resolves to the correct API path without hand-building it, which is what keeps the setup and game endpoints decoupled from a hardcoded URL.

Security note: the tag and mode values traveling in the query string get echoed straight back into href and hx-get attributes on every screen. Run them through UrlEncode before rebuilding any URL from them, or a crafted query string could break out of the attribute and inject markup.

Setting up the game endpoint's list field

The setup screen's List field uses Rock's built-in {[ dropdown ]} shortcode rather than a hand-rolled <select>, with the options built dynamically from the tag query above: 

{[ dropdown label:'List' name:'tag' longlistenabled:'true' isrequired:'true' ]}
  [[ item value:'' text:'-- Choose a List --' ]][[ enditem ]]
  {% for t in tags %}
  [[ item value:'{{ t.Id }}' text:'{{ t.Name }}' ]][[ enditem ]]
  {% endfor %}
{[ enddropdown ]}

That shortcode's own markup carries a small inline script that initializes the enhanced, searchable dropdown, and it re-runs every time the shortcode's output is generated, including on an HTMX swap. That is what lets it work reliably even though this screen is delivered as a swapped fragment rather than a fresh page load.

Two ways to deploy

OptionWhat it isTrade-off
Lava Application (recommended) One Lava Application with two LavaEndpoints (setup and game) plus a host page using the Lava Application Content Block. A LavaEndpoint's own URL is a bare API path with no site chrome, so the address bar is never updated. A refresh mid-game always returns to the setup screen.
Single-file fallback One self-contained plain HTML Content block, no Lava Application setup required. Preserves progress across a refresh and degrades to real href navigation if HTMX fails, at the cost of not being a "real" Lava Application.

Both require Rock 18.0+ and the same Tag-based sourcing described above.

Optional: the "more about this person" panel

Both endpoints support a collapsed-by-default panel, shown after a card is answered or revealed, with campus, connection status, how long the person has been tagged with the list being played, household members, and up to three other non-family groups. It is controlled by a checkbox on the setup screen, threaded through the game the same way the score-tracking checkbox is. The excluded group type (Family, by default) is a single hardcoded GroupType GUID near the bottom of the endpoint file, easy to change if a church wants a different exclusion.

Validation checklist

Work through each of these before considering the game ready for real use:

  • A correct guess scores and advances to the next person.
  • An incorrect guess does not score and gives clear feedback.
  • People without a photo are never shown.
  • A page reload does not break the game or double-count the score.
  • The block only shows people the current user is permitted to see.
  • HTMX swaps update only the intended region, with no full page reload.
  • A tag with no eligible people shows a clear message instead of erroring.

Where this technique goes next

Nothing about this pattern is specific to a guessing game. A Lava block that pulls a random or filtered record, renders a fragment, and swaps itself with HTMX on every interaction is a template for anything that needs partial-page interactivity without a JavaScript framework: a quiz, a flash-card review, a rotating prayer request, a serving-team check-in. The game is the approachable wrapper. The technique is the reusable part.
